# همگام‌سازی (Sync)

این سند رفتار همگام‌سازی را همان‌طور که هست توصیف می‌کند. طبق B2a، منطق سینک **تغییر نکرده** است؛ فقط جدول‌های تازه (P1، R1–R3، G1) به فهرست مجاز اضافه شده‌اند.

## سیاست تعارض، در دو خط

**آخرین نوشتن برنده است، بر اساس `updatedAt` که خودِ گوشی می‌فرستد.** ردیفی که `updatedAt` بزرگ‌تری دارد جایگزین می‌شود و ردیف قدیمی‌تر هرگز روی جدیدتر نمی‌نویسد.

**پیامدش را بدانید:** `updatedAt` ساعتِ گوشی است، نه ساعت سرور. اگر ساعت یک گوشی اشتباه باشد (مثلاً یک سال عقب)، ویرایشی که امروز روی آن گوشی انجام شده ممکن است در برابر ویرایش دیروزِ گوشی دیگر ببازد. این یک نقص شناخته‌شده و پذیرفته‌شده است و در MVP تغییری نمی‌کند.

## چه چیزی همگام می‌شود

| جدول | همگام می‌شود؟ |
|---|---|
| `tasks`, `done`, `birthdays`, `people`, `tags`, `personTags`, `personNotes`, `interactions` | بله |
| `skills`, `personSkills`, `ratings`, `relationships` | بله |
| `photos` (فقط متادیتا) | بله |
| `ruleCategories`, `rules`, `ruleReviews` | بله (قوانین من) |
| `compareSessions`, `compareItems`, `compareChecks` | بله (مقایسهٔ خرید) |
| `ruleBreaks`, `ruleChecks`, `ruleCheckItems` | بله (ثبت شکستن و بررسی قوانین برای یک آدم) |
| `exchanges`, `exchangeSettlements` | بله (دادوستد) |
| `photoFiles` | **هرگز** — فایل عکس روی دستگاه می‌ماند (آپلود آن کار B2b است) |
| `outbox` | هرگز — صف محلی تغییرات است |

هر دو فهرست باید یکی بمانند: `TABLES` در `src/db.ts` و `TABLES` در `worker/index.ts`. اگر جدولی فقط در کلاینت باشد، ردیف‌هایش بی‌صدا رد می‌شوند.

## چطور کار می‌کند

- هر ردیف به‌صورت یک رشتهٔ JSON فرستاده می‌شود؛ سرور آن را همان‌طور ذخیره می‌کند (رمزنگاری ندارد).
- سرور برای هر حساب یک `clock` یکنوا دارد که با هر push یکی بالا می‌رود. کلاینت آن را به‌عنوان نشانگر pull نگه می‌دارد (`since`).
- هر نوشتن محلی از `put`/`del` در `db.ts` رد می‌شود و یک ردیف در `outbox` می‌گذارد. سینک فقط `outbox` را می‌فرستد.
- حذف = حذف سخت + یک سنگ‌قبر (`deleted: 1`) در `outbox` تا حذف هم منتقل شود.
- سینک فقط وقتی روشن است و فقط وقتی برنامه باز است اجرا می‌شود.

## بازیابی روی گوشی نو

همان ورود با ایمیل و رمز: پس از `connect`، دادهٔ محلی با نسخهٔ ابری **ادغام** می‌شود (جایگزین نمی‌شود). حالت «همه را پاک کن و از سر بنویس» وجود ندارد.

فایل‌های عکس در این مرحله با سینک نمی‌آیند: اول متادیتا می‌آید و بعد (با B2b) فایل‌ها دانلود می‌شوند.

## چه چیزی در همان‌جا نشان داده می‌شود

صفحهٔ «حساب و پشتیبان» (و ردیف همگام‌سازی در تنظیمات) وضعیت را نشان می‌دهد: آخرین زمان همگام‌سازی، تعداد تغییرات در انتظار ارسال، و فهرست چند مورد اول از صف.

## فایل عکس‌ها (B2b)

فایل عکس‌ها از سینک ردیف‌ها جدا هستند و در R2 ذخیره می‌شوند:

- **مسیرها:** `PUT /api/photo/<id>` برای آپلود، `GET /api/photo/<id>` برای دانلود، `GET /api/photo` برای فهرست شناسه‌هایی که سرور دارد.
- **دسترسی:** با همان کلید Bearer. کلید بدون حساب ثبت‌شده پیش از هر کاری `401` می‌گیرد، پس کلید ساختگی نمی‌تواند فایل دیگران را پیدا کند.
- **جداسازی:** کلید هر فایل با هش حساب شروع می‌شود (`<account>/photos/<id>.jpg`)، پس دو کاربر با شناسهٔ یکسان هرگز به فایل هم نمی‌رسند.
- **بدون تکرار:** شناسهٔ عکس همان چیزی است که سمت کلاینت ساخته شده، و آپلود دوباره همان کلید را بازنویسی می‌کند — retry ردیف دوم نمی‌سازد.
- **سقف‌ها:** ۳۰۰ عکس برای هر کاربر، ۱٫۵ مگابایت برای هر فایل، و سقف اندازهٔ درخواست. آپلودها هم rate-limit دارند.
- **صف:** فایلی که تازه اضافه شده وضعیت `local` دارد؛ آپلود موفق آن را `uploaded` و شکست آن را `failed` می‌کند تا دور بعد دوباره تلاش شود. فایل محلی هیچ‌وقت در اثر شکست آپلود پاک نمی‌شود.
- **بازیابی:** گوشی نو اول متادیتا را از سینک ردیف‌ها می‌گیرد، بعد فهرست سرور را می‌پرسد و فقط فایل‌های گمشده را دانلود می‌کند.
- **وقتی حساب وصل نیست** هیچ‌کدام از این‌ها اجرا نمی‌شود.

### کجا ذخیره می‌شود: R2 یا D1

سرور خودش انتخاب می‌کند و کلاینت هیچ تفاوتی نمی‌بیند:

1. **R2** اگر binding به نام `PHOTOS` وجود داشته باشد (مسیر اصلی و مورد نظر spec).
2. **D1** در غیر این صورت: فایل به تکه‌های ۵۰٬۰۰۰ کاراکتری base64 شکسته می‌شود (`photo_chunks`) و یک ردیف خلاصه در `photo_files` نگه داشته می‌شود.

دلیل وجود گزینهٔ دوم: فعال کردن R2 فقط از داشبورد Cloudflare ممکن است و از طریق API/wrangler انجام نمی‌شود (خطای `10042`). بدون این گزینه، پشتیبان عکس‌ها تا ابد کار نمی‌کرد.

**نتیجهٔ تست واقعی روی سرور (حالت D1):**

- آپلود یک JPEG کوچک → `200`، فهرست یک مورد را نشان می‌دهد، دانلود **بایت‌به‌بایت یکسان**.
- آپلود دوبارهٔ همان شناسه → تعداد **۱** می‌ماند (بدون تکرار).
- فایل ۸۷۹ کیلوبایتی → `200`، ۲۵ تکه، دانلود ۹۰۰٬۰۰۰ بایت **کاملاً یکسان**، حدود ۴ ثانیه.
- فایل ۱٫۶ مگابایتی → `413`. فایل غیر-JPEG → `400`.

**برای رفتن به R2 (وقتی فعال شد):**

```bash
npx wrangler r2 bucket create halgheh-photos
# بلوک r2_buckets را در wrangler.jsonc از کامنت خارج کن
npx wrangler deploy
```

از آن لحظه سرور خودکار از R2 استفاده می‌کند؛ هیچ تغییری در اپ لازم نیست، و فایل‌های قدیمی در D1 همچنان خوانده می‌شوند (بهتر است یک بار دوباره آپلود شوند).

## دو نقص پذیرفته‌شده

1. **ساعت گوشی ملاک است** (بالا توضیح داده شد).
2. **یک pull که با push دستگاه دیگر مسابقه بدهد** ممکن است آن push را تا تغییر بعدی نبیند.
